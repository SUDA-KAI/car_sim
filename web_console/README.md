# NAV STUDIO · 仿真导航工作台

直接连接本机 ROS 2 Humble / Gazebo Fortress / Nav2 的中文网页控制台。前端为原生 HTML、CSS、Canvas 与 JavaScript，后端为 Python 标准库 HTTP 服务和 `rclpy`，没有 npm 构建步骤，不依赖外部 CDN。

## 启动

在工作区执行：

```bash
cd /home/a/ros2_ws/gz_sim
./run_web_console.sh --open
```

浏览器访问 **http://127.0.0.1:8770**。`--open` 只负责打开浏览器，不会自动启动小车；仿真由网页按钮启动。

也可以双击 `导航仿真工作台.desktop`，或在终端使用自定义端口、仿真域：

```bash
./run_web_console.sh --port 8771 --domain 74
```

默认使用独立的 **ROS_DOMAIN_ID=73** 和 **IGN_PARTITION=patrol_web_console_73**，与原有 `run_sim.sh` 的 42 域、`patrol_sim` 分区区分。`--domain` 改变 ROS 域时，Gazebo 分区也跟随改变；可用 `--partition` 显式覆盖。不能使用实车默认域 0。启动前检查 ROS 域占用，同一用户的同一域只允许启动一个网页控制台。

## 使用流程

1. 在左侧选择场景。自动发现 `worlds/`、`test_scenes/worlds/` 中配有地图元数据的场景，包括现场地图、实验场、窄道、坡道、摩擦场景。
2. 在右侧选择场景默认控制器、MPPI 或 TEB，设置定位和速度上限。默认保留现有的车模、传感器安装及 Nav2 配置。仿真运行期间配置锁定，先停止再切换。
3. 点击“启动仿真与导航”。勾选“三维窗口”会打开本机 Gazebo；关闭则使用已有的无界面渲染启动方式。通常需等待 30–60 秒，繁忙机器可能更久。
4. 等待时钟、`map → base_link` 定位、`bt_navigator` 生命周期同时就绪。
5. 选择地图工具栏“◎”，点击空闲区域添加目标；单击默认沿用当前小车朝向（没有实时位姿时用出生朝向），按住拖动可指定朝向。目标队列内也可直接编辑到达角度。可载入场景预设路线、删除单点或清空队列。
6. 点击“检查路径”，调用 Nav2 `ComputePathToPose` / `ComputePathThroughPoses` 绘制真实路径，该操作不启动车辆。空闲像素不代表阿克曼小车一定可达。
7. 选择“逐点到达”或“连续经过目标点”，点击“开始导航”。网页先自动检查路径，成功后才发送原生 Nav2 导航 Action；检查失败会显示原因，不进入反复倒车/等待恢复。完成、失败和取消状态来自 Action 结果。路径检查通过也不保证动态障碍、定位或局部跟踪一定成功。
8. 用“取消任务”取消当前导航或路径检查，用“停止仿真”停止控制台启动的整组进程。退出控制台（Ctrl+C 或 SIGTERM）也会关闭所属仿真。

网页提供“路径搜索时限”，默认 20 秒，范围 1–60 秒。大地图上较远目标比约 1–2 m 的短巡逻目标需要更多搜索；超时返回空路径不能直接判定几何上不可达。该选项只改变仿真启动时生成的规划参数，不改变地图分辨率、车身轮廓、转弯半径或未知区策略。原来的 `run_sim.sh` 默认保留场景时限，也可显式指定 `planning_timeout:=20`。不在导航运行中动态改该参数，避免规划器重建搜索表时影响生命周期服务。

滚轮缩放地图，拖动平移，“⌗”适应地图，“⌖”跟随车辆。可切换规划路径、激光和历史轨迹图层。初始位姿工具“➤”向 AMCL 发布 `/initialpose`，只用于定位修正，不会传送 Gazebo 车模；真值定位场景禁用该操作。

## 导入地图

点击左下角“导入自定义地图”，提供 ROS 地图 YAML 和其 `image` 指向的 PGM / PNG 图像。图像文件名需与 YAML 中 image 的文件名一致。支持 `trinary`、`negate`、地图原点旋转及原始分辨率，最多 600 万像素、图像文件最多 12 MB。

系统查找具有 **0.8 m 已知空闲余量** 的出生位置，复用 `scripts/build_world.py` 挤出占据单元作为墙体，生成 SDF 与元数据。可设置 0.2–5 m 墙高。导入结果保存在 `web_console/data/maps/custom_*/`，不会改写原始地图或场景；生成失败会清理该次目录。

二维地图只能生成平地与墙体，不会推断真实地面坡度。测试库中的坡道沿用现有三维场景；网页地图仍是俯视占据地图。窄弯、低摩擦等场景是否能成功导航，取决于现有控制器、定位与场景条件；网页如实显示成功或失败，不把预设路线当作已通过测试。

## 可视化与接口

| 数据 | 来源 |
| --- | --- |
| 小车 map 坐标、航向、轨迹 | TF `map → base_link` |
| 线速度、角速度 | `/chassis/odom` |
| 仿真时间与连接状态 | `/clock` |
| 规划路径 | `/plan`，仅显示 map 坐标系路径 |
| 激光点 | `/scan`，经传感器 TF 变换到 map |
| 四路超声波 | `/ultrasonic_1` 至 `/ultrasonic_4` |
| 导航状态、剩余距离和恢复次数 | `/navigate_to_pose`、`/navigate_through_poses` |
| 导航可用状态 | `/bt_navigator/get_state`，需为 active |

遥测通过每 700 ms 的同源 HTTP 请求读取。没有新数据时隐藏激光/测距，连接中断时车辆和指标不继续更新。停止或重新启动仿真时清空旧时钟、TF 缓存与遥测，避免把上一场景数据当成当前状态。浏览器刷新后可恢复正在执行的目标列表。

日志面板可筛选警告与错误，并导出当前浏览器保留的日志。服务端保留最近 400 条，浏览器最多保留 1800 条。

## 局域网访问

```bash
./run_web_console.sh --host 0.0.0.0 --port 8770
```

其他设备访问 `http://仿真主机IP:8770`；Gazebo 三维窗口仍显示在仿真主机。该控制台默认只监听本机，不含账号认证，局域网模式适用于可信实验网络。它必须运行在能直接使用 ROS/Gazebo 的主机上。

## 验证

```bash
cd /home/a/ros2_ws
python3 -m unittest discover -s gz_sim/tests -p test_web_console.py -v
node --check gz_sim/web_console/static/app.js
```

测试覆盖现有地图、旋转坐标、新地图场景生成、失败清理、非法坐标/阈值、域隔离、静态文件访问范围和跨站请求限制。

本次检查记录位于 `../artifacts/web_console_*.json` 和 `web_console_tests.log`：13 项自动化测试通过；浏览器验证了实际目标发送、路径反馈、车辆移动、取消任务、刷新恢复、地图上传和桌面/手机布局。另在 `narrow_17` 接收到 267 个激光点与四路超声波读数；连续目标任务中原有 MPPI 反复中止 FollowPath、车辆没有前进，该任务已取消，未将其计为路线成功。网页接入验证不等于原有各场景控制器全部通过。

接口实现参考 [Nav2 Humble NavigateToPose](https://api.nav2.org/actions/humble/navigatetopose.html)。


## 2026-11-02 网页目标朝向与路径检查修正

日志中的目标 `(5.01, -0.03)` 与历史成功的上方通道短巡逻不是同一个任务。初版网页单击的默认朝向为 0°，且只验证目标像素为空闲，缺少原生规划预检查；这会把“位置可选”误当成“目标位姿可达”。现已修正默认朝向，提供角度编辑和不启动车辆的路径检查。

对照记录 `../artifacts/web_navigation_goal_yaw_audit.json`：同一坐标朝向约 18.6°、−29.8° 未返回路径，−161.4° 成功返回约 18.5 m 的路径（本机该次搜索约 14.7 秒）。这说明到达朝向与搜索预算都会影响结果，不能将空路径直接归因于 TEB/MPPI 控制器。路径成功不等于整段驾驶已经通过。

原成功路线已通过网页 HTTP/ROS 接口重放，4/4 航点成功、恢复次数为 0，记录在 `../artifacts/web_navigation_fix_verification.json`。当前自动化检查包含 15 项控制台测试与 6 项导航配置测试；浏览器验证记录另存 `web_console_navigation_fix_browser.json`。
